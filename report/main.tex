\section{Project Overview}
\label{sec:intro}

\textit{Gipfelsturm} (German: ``summit attempt'') targets \textbf{Challenge 2}: achieving the highest tokens/sec/GPU for a given model size on a single node (4$\times$GH200 GPUs) of the CSCS Alps supercomputer. We use Megatron-LM ~\cite{shoeybi2019megatron} as the training framework and systematically explore three orthogonal optimization axes : compute kernels, precision, memory strategies, and intra-node parallelism. The best techniques are then combined.

Our three-phase approach (familiarization, independent exploration, integration) lets each team member own one axis while sharing a common benchmark harness. The final configuration targets a $\sim$8B parameter model on a single GH200 node with 4 GPUs.


\section{Implementation}
\label{sec:implementation}

\paragraph{Intra-node Parallelism.}

Alps has two network speeds: inside a node GPUs talk over NVLink at about 340 GB/s and between nodes over Slingshot at about 93 GB/s, roughly 3.7$\times$ slower. We know that tensor parallelism adds all-reduces in every layer, in both the forward and backward pass. That traffic is likely only tolerable at NVLink speed, so any TP we use should stay inside a node.

TP tends to buy memory at the cost of throughput. Each shard shrinks the local GEMMs and adds collectives that are hard to fully hide. We only want to pay that price when memory forces us to.

The 8B model fits at TP=1 with a peak of about 88 GB per GPU, out of 96 GB. The theoretical footprint is higher. Indeed, weights and optimizer state alone are roughly 63 GB and untouched activations would likely push the total past capacity. Two things bring it down: (1) the distributed optimizer shards the optimizer state across the four DP ranks and (2) selective activation recomputation drops the heaviest activations. With both on we land at 88 GB, which suggests there is little left for TP to solve.

That gives us a fairly clear prediction. Any TP $>$ 1 should mostly cost throughput here. It would shrink the GEMMs and add collectives without freeing memory we appear to need. The same reasoning suggests sequence parallelism is unlikely to help. It requires TP $\geq$ 2, and the activation memory it would save is memory we do not seem to be short on.

\paragraph{Precision \& Memory.}
We study precision and memory as a joint optimization axis. Starting from a BF16
baseline, we evaluate FP8 training with TransformerEngine and FP8 optimizer states
to reduce HBM usage while exploiting GH200-native FP8 tensor cores. We then test CPU
offloading of optimizer states, together with reduced sequence length, as a mechanism
to trade sequence length for larger micro-batch size at TP=1. We also assess activation
recomputation as a memory--throughput tradeoff and compare BF16 and FP8 loss curves
over 500 steps to verify numerical stability.
\paragraph{Compute Kernels.}
NSYS profiling identifies the dominant kernels in the baseline configuration. We then evaluate FlashAttention (\texttt{--use-flash-attn}), Liger-Kernel fused operators (RMSNorm, SwiGLU, cross-entropy), Cut Cross-Entropy, and \texttt{torch.compile}. Each optimization is measured independently and stacked, probing whether kernel-level fusion offers any headroom on top of the TransformerEngine backend.

\section{Experiments}
\label{sec:experiments}

\subsection{Parallelism Sweep}

\paragraph{Tensor parallelism ablation.}
Figure~\ref{fig:tp_ablation} reports per-GPU throughput as a function of the tensor parallelism degree, with TP$\cdot$DP$=4$ held fixed on a single GH200 node and the global batch size (256) and sequence length (4096) kept constant across runs. The trend is consistent with the prediction in Section~\ref{sec:implementation}: throughput per GPU appears to decrease as TP grows, with TP=1 giving the highest rate, and the sequence parallel variants we tried do not seem to recover the loss. Based on these results we keep TP=1, DP=4 as the single-node configuration and drop the TP $>$ 1 and sequence parallel runs from the rest of the study.

\subsection{Precision \& Memory}

BF16 serves as the baseline configuration. Enabling FP8 with TransformerEngine and
quantizing Adam moment states to FP8 improves throughput from 10,945 to 15,306 tok/s/GPU,
a +39.8\% gain over BF16.

FP8 alone was not viable at this scale. In our setup, TransformerEngine delayed-scaling
metadata, including amax history buffers (\texttt{amax\_history\_len=1024}), offset the
expected memory savings and caused OOM; FP8 therefore had to be paired with FP8 optimizer
states to achieve a net memory reduction.

\subsubsection{Memory Reduction Strategies}

The main memory gain comes from shortening the sequence and using the recovered headroom
to increase micro-batch size. In particular, reducing sequence length from 4096 to 2048
allowed MBS to increase from 2 to 4, and reducing it to 1024 allowed MBS to increase to 8.

This trade is not memory-neutral, even when $\text{seq len} \times \text{MBS}$ is held
constant. Attention-related activations grow disproportionately with sequence length, so
shorter sequences free more memory than a linear token-count argument would suggest.
CPU offloading further reduces HBM pressure by moving optimizer states to Grace host
memory, but in these experiments its role is secondary to the sequence-length--micro-batch tradeoff.

\subsubsection{ZeRO and Gradient Checkpointing}

ZeRO-1 is enabled in all runs. ZeRO-2, ZeRO-3, and activation recomputation were not
pursued at 8B scale because this regime is not sufficiently memory-constrained to justify
their additional communication or recompute overhead.

\textbf{All optimizations show neutral-to-negative impact} ($-$1\% to $-$3\%). NSYS profiling (trace file included in submission as \texttt{nsys\_traces/trace\_baseline.nsys-rep}) confirms the root cause: TransformerEngine occupies $\sim$99.8\% of the default CUDA stream with its own fused \texttt{nvte\_*} kernels throughout each iteration. The GPU is already saturated — there is no idle time for additional kernel fusion to exploit.

Concretely: (1)~\textbf{FlashAttention} is redundant because TE's \texttt{TEDotProductAttention} uses an equivalent fused attention path internally; adding \texttt{--use-flash-attn} on top of TE introduces a conflict that costs 2.9\%. (2)~\textbf{Liger-Kernel} v0.8.0 does not yet support \texttt{apply\_liger\_kernel\_to\_megatron} (open PR \#1207 as of May 2026); we manually patched \texttt{FusedRMSNorm} with \texttt{LigerRMSNorm}, but TE overrides the norm computation with its own fused path, rendering the patch a near no-op with $-$1\% overhead from the wrapper. (3)~\textbf{torch.compile} is incompatible with Megatron-LM's DDP hook implementation in \texttt{core\_v0.16.1}.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{pareto_chart.png}
  \caption{Kernel optimization results on the 8B model. Left: throughput under TE backend — all optimizations show neutral-to-negative impact. Right: removing TransformerEngine (local TP=4) yields 2.3$\times$ lower throughput, confirming TE is a prerequisite.}
  \label{fig:pareto}
\end{figure}

\textbf{TransformerEngine is a prerequisite, not an optimization.} To quantify TE's contribution, we ran the same 8B model with \texttt{--transformer-impl local} (Megatron's native PyTorch implementation). TP=1 and TP=2 failed with CUDA OOM (96\,GB GH200) — without TE's fused kernels, the O($n^2$) attention matrix and unoptimized gradient buffers exceed GPU capacity at GBS=256. Using TP=4 resolves the OOM and yields \textbf{4{,}878 tok/s/GPU}, which is \textbf{2.26$\times$ slower} than the TE TP=1 baseline. This confirms that TransformerEngine is not an optional add-on but a hardware-level prerequisite for efficient 8B model training on GH200.

\subsection{Discussion}

Our three-axis methodology isolates each optimization family's contribution and reveals a clear hierarchy. The \textbf{precision axis} (Gaspard) delivers the largest gains: FP8 with FP8 optimizer states and CPU offloading yields \textbf{+52.7\%} over BF16. The \textbf{parallelism axis} (Baudoin) confirms TP=1 is optimal for 8B on a single node, since the model fits in memory without tensor parallelism and TP overhead outweighs any benefit. The \textbf{compute-kernel axis} (Rayane) finds that application-layer kernel optimizations (FlashAttention, Liger-Kernel, \texttt{torch.compile}) provide no benefit on top of TransformerEngine — TE's hardware-aware CUDA kernels already saturate the GPU at $\sim$99.8\% stream utilization, leaving no idle time for additional fusion.

A key cross-axis finding is that TransformerEngine is not an optional add-on: removing it causes 2.3$\times$ throughput regression even at TP=4. This has practical implications for kernel research on GH200 — future kernel optimization efforts should target the narrow set of operations outside TE's scope (e.g.\ vocabulary-parallel cross-entropy), rather than re-implementing what TE already fuses.
